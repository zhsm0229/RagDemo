# AI 开发全过程方法论（RagDemo 实战提炼）

一套经过八个开发波次（W1-W6 基建到加固、两次检索优化波、一次全量测试修复波）实战验证的工作纪律。它回答一个问题：**如何让 AI 代理团队在长周期项目中持续交付高质量代码，而不靠运气和口头约定。**

## 总循环

```
立项（三件套）→ 立约束（宪法+红线）→ 设计（spec 评审冻结）→ 拆工单（含失败测试）
   → TDD 波次（多代理团队）→ 评审裁决 → 提交（脚本通道）→ 门禁复跑 → 收口（台账+报告）
   → 演进（按触发线，不按日历）→ ↩ 下一迭代
```

任何阶段都有"产物"和"门禁"：产物落盘（文档/工单/台账），门禁不过不进下一阶段。**跳阶段省下的时间，会在后期以十倍代价还回来**——这条是全套方法论的第一公理。

## 七阶段核心纪律

### 1. 立项：先写三件套，再写第一行业务代码

- 项目入口用 AGENTS.md（约束汇总+红线+唯一可高频改写的状态节），规范基线用 standards.md（版本化宪法），操作细节用 playbook.md（场景式手册）。三件套写法见 `references/bootstrap.md`。
- 门禁：三件套评审通过前不启动编码——"边写边补规范"等于没有规范。
- 📌 RagDemo 实例：AGENTS.md 头部固定三行元数据（定位/对账日期/同步保障），"当前状态"是全文唯一允许高频改写的段落，其余段落修改走评审。

### 2. 约束：宪法式规范 + 红线清单 + 触发线

- 架构约束的通用模式：**分层单向依赖 + 可替换点接口化**。实现类只在装配层选择，业务代码面向接口。
- 红线是"违反=不合入"的评审强制检查项，数量控制在 5-8 条——多了记不住，等于没有。
- 演进按触发线不按日历：**未到触发线禁止提前建设**，用禁清单把诱惑显式写下来。
- 详见 `references/constraints.md`。

### 3. 文档：三档生命周期 + 单一真相源 + 数字守账

- 文档分三档：**活文档**（永远代表现状，改代码必须同步）、**快照**（时点记录，日期前缀，写完冻结）、**台账**（过程流水，只增不改）。
- 每项信息只有一个"家"，他处只放指针+一句话摘要。
- 会漂移的数字必须有守账测试背书，写法固定："端点总数 66，由 `tests/unit/test_api_contract.py` 对账"。无守账的动态数字禁入正文。
- 详见 `references/docs-system.md`。

### 4. 设计：spec 要可裁决

- 中等以上变更先写 spec 再编码，骨架固定：头部版本状态 → 目标/非目标 → 门槛分类（A 资源/B 证据/C 纪律）→ 方案参数表（**缺省=现状行为**）→ 测试 seams（冻结）→ 验收阈值 → 裁决记录（编号+角色溯源）。
- 头部写明"编码必须严格遵循本文档；冲突先评审指出，不许静默择一"。
- 详见 `references/design-specs.md`。

### 5. 流水线：工单 → TDD 波次 → 评审 → 提交 → 收口

- 工单一票一文件，内嵌**失败测试代码**（Step 1 就是红），Files/Interfaces 精确到路径。
- 波次按"文件面互斥"划分，保证并行安全。
- 提交走脚本通道（显式路径 add + heredoc 提交消息 + 门禁行），日常禁 `git add -A`。
- 收口四件套：全量回归+前端四门 → 打 tag → staging 部署+冒烟 → 迭代报告归档。
- 模板与细则见 `references/pipeline.md`。

### 6. 测试：红绿证是信仰

- TDD 三步：先写失败测试（红必须是"功能未实现"式的红）→ 最小实现 → 通过。测试没红直接绿 = 停下来，说明测的不是你以为的东西。
- 写库测试必须带读回断言；断言精确，禁止 `A or B` 宽松断言。
- bug 修复先写复现测试再修，复现测试永久保留。
- 会漂移的业务数字用守账测试锁住。
- 详见 `references/testing.md`。

### 7. 协作：人机分工与多代理团队

- AI 会话四步走：复述验收标准 → 只读探索给现状 → 产计划不写码 → 人确认后才写码。编造现状 = 立即纠偏。
- 大波次用多代理团队公式：PM 总协调 / 架构师技术总责 / 设计师 UI 把控 / 开发×N 按波次 TDD / 测试验收——先组织评审刷新规范文档，再严格按文档编码。
- 并行会话改共享文件前先重读；密钥/真实数据/生产库禁贴 AI。
- 详见 `references/collaboration.md`。

## 纪律冲突处理

规范与实现冲突、本文档与项目实际文档冲突时：**先在评审中指出矛盾，不许静默择一**。裁决结果回写规范并登记（裁决表），让下一次不再纠结同一件事。

## 实战教训索引（每条都花过真实代价）

- 17 位纯数字流水号被银行卡敏感扫描命中（约 1/10 概率过 Luhn）→ 测试夹具数据要过一遍产品的校验/扫描逻辑。
- docker build 失败被管道 `tail` 吃掉退出码 → 构建输出重定向文件后显式检查 `$?`。
- 门禁与评测长跑并行 → 容器被 OOM 杀（exit 137）→ 8G 级机器严禁资源密集任务并行。
- 单例带实例计数的状态机跨请求串票 → 无状态化（按输入判定进度）。
- watchfile/超时参数改了实现忘改测试断言 → 参数变更与守账断言同 commit。
