# 约束体系：宪法式规范 + 红线 + 触发线

项目约束不是文档装饰，是**评审的强制检查项**。本文件讲三类约束怎么定、为什么这么定。

## 一、架构约束的通用模式：分层单向 + 接口化替换点

**模式**：把系统按职责分成单向依赖的层（上层可用下层，禁止反向），并把"将来可能换实现"的点一律抽象成接口，实现类只允许在装配层（依赖注入处）选择。

**为什么**：单向依赖让每次改动的波及范围可预测；接口化让外部依赖（LLM、向量库、存储）可以在不碰业务代码的情况下替换——换供应商、换本地/云、换真机/Stub 都只是装配层一行。

**📌 RagDemo 实例**：五层 `api → services → rag → core → db`，六个可替换点接口化（LLMProvider / VectorStore / Parser / Embedder / Reranker / FileStorage）。后来从"云 LLM"切到"DeepSeek 云轨"、测试切"Stub 三件套"，业务代码零改动。

**配套细则**（按需采纳）：
- 单文件 ≤300 行、单函数 ≤50 行——行数红线逼着拆模块，注释里写"为什么拆"；
- 禁裸 `except:`——吞异常是事故放大器；
- 外部调用必设超时 + 一次重试（按调用类型分级：生成类 60s、向量化 10s、解析 300s）；
- 跨模块取数必须走对应 service 函数，api 层禁止直写 SQL——数据访问口径只有一份。

## 二、红线清单：违反=不合入

红线是**评审会上逐条对照的强制检查项**，不是建议。定制原则：

1. **数量 5-8 条**——多了评审记不住，等于没有；
2. 每条必须**可机械检查**（grep 得到、测试能断言），不许写"注意安全"这类空话；
3. 覆盖三类：**安全**（注入/越权/密钥）、**数据**（隔离/软删/迁移）、**产品验收红线**（产品承诺过的底线行为）。

**📌 RagDemo 实例（7 条）**：部门隔离+IDOR 归属校验；SQL 一律参数绑定；知识不足必须拒答绝不编造（产品验收红线）；密钥只走 `.env` 仓库只留 example；上传三重白名单+解压上限；LLM 约束（max_tokens 服务端钳制、召回内容包裹不可信声明）；提交前七项自查。

**为什么拒答写进红线**：RAG 类产品"编造答案"是验收一票否决项。把产品底线写进工程红线，评审才有抓手——**产品承诺要转化为工程可检查项**。

## 三、触发线演进：按触发线不按日历

**模式**：把"将来才需要的能力"写成**触发条件 + 到达后的动作序列**，并维护一份**禁清单**（禁止提前建设的东西）。

**为什么**：过度建设是真金白银的成本+维护负担；但"永远不做"又会堵死退路。触发线把两难变成显式决策：现在不做，但写清楚"什么时候做、做之前先干什么"。

**到达触发线的动作序列**：写一页式 ADR（背景/选项/决策）→ 修订 standards → 评审 → 实施。

**📌 RagDemo 实例**：设计按 100x 规格一次到位，建设按触发线分期。禁清单 9 项（Milvus、K8s、微服务、细粒度 ACL、语义缓存等）；检索优化按 A 资源门槛 / B 证据门槛（须四指标跑分对比）/ C 纪律永久门 三分类——每项"暂时不做"的能力都写明解锁条件。

**配套纪律——退路保留**：新模块不得堵死预留退路，设计评审把"是否堵死退路"列为检查项。📌 实例：无状态 JWT（为横向扩容留路）、dept→ACL 演进预留。

## 四、约束的落地位置

| 约束类型 | 落点 | 维护方式 |
|---------|------|---------|
| 架构分层/接口化 | standards §1 + AGENTS.md 摘要 | 结构变更走评审 |
| 红线 | AGENTS.md"硬性红线"节（评审强制对照） | 新增需评审，删除需论证 |
| 触发线/禁清单 | standards §25 + ADR | 触发线到达时按序列启动 |
| 行数/超时等细则 | standards 对应章节 + lint/CI 强制 | 随门禁演进 |
