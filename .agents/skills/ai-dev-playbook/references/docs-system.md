# 文档三档制：活文档 / 快照 / 台账

文档体系的目标只有一个：**半年后任何人对系统的任何疑问，都能在 30 秒内找到唯一可信的答案**。三档制、单一真相源、数字守账都是为这个目标服务的。

## 一、三档生命周期

| 档位 | 定义 | 命名 | 写完之后 |
|------|------|------|---------|
| **活文档** | 永远代表现状，改代码必须同步对应文档 | 固定清单（standards/api/runbook/user-guide/入口文档） | 随代码持续更新，受评审保护 |
| **快照** | 时点记录（评审报告/验收状态/测试报告） | ISO 日期前缀（`2026-10-11-全量测试报告.md`） | 写完即冻结；被取代后移 `archive/` |
| **台账** | 过程流水（工单/回执/评审 diff/进度） | 按波次分目录（如 `.superpowers/sdd/<日期-波次>/`） | 只增不改，**不作为现状依据** |

**为什么分档**：文档腐烂的根源是"时点记录冒充现状"（半年前的评审报告被人当设计依据）和"同一信息多处维护"（改了一处忘三处）。分档+冻结+只增不改，从机制上切断这两条腐烂路径。

## 二、单一真相源

每项信息只有一个"家"；其他位置只放**指针 + 一句话摘要**。

- 📌 实例：接口契约的家是 `docs/api.md`；AGENTS.md 里只写"端点总数 66，契约见 api.md"。
- 反例：两处各自维护"部署步骤"清单——改了一处忘另一处，新人照着旧清单操作直接翻车。

**新增文档必须先回答：这项信息的家是不是已经存在？** 是 → 更新既有文档；否 → 新建并登记到文档地图。

## 三、数字守账（本项目最有价值的发明之一）

**规则：会漂移的数字必须由守账测试背书，正文用固定写法注明；无守账的动态数字禁入正文。**

固定写法：`端点总数 66（本行由 tests/unit/test_api_contract.py 从 FastAPI 实际路由解析校验）`。

**为什么**：文档里的数字（端点数、用例数、阈值、超时）注定随代码漂移，人工维护必然漏。守账测试把"文档数字是否与实现一致"变成 CI 门禁——数字漂了测试红，比任何评审都可靠。

**怎么做**：为每个会漂移的数字写一个断言测试（解析实现真实状态 vs 文档标记行）；文档侧在数字旁标注守账测试路径。

## 四、活文档头部元数据与同步义务

活文档头部固定三行：

```markdown
> 定位：<本档角色>｜对账：<YYYY-MM-DD>｜同步保障：<哪个机制保证它不烂>
```

**同步义务三绑定**（改了什么就必须同步什么）：
1. 接口改 → 同步 api.md 的契约标记行（守账测试兜底）；
2. 界面文案改 → 同步 user-guide 与前端帮助源（📌 实例：文案三源联动，grep 零残留才算完）；
3. 里程碑收口 → 更新入口文档"当前状态"节。

**引用完整性**：文档与注释引用的命令、文件、路径必须真实存在——引用 404 比没有引用更糟。

## 五、台账纪律（多代理开发的记忆系统）

台账（`.superpowers/sdd/<波次>/`）记录完整过程：`task-N-brief.md`（派工）→ `task-N-report.md`（回执）→ `review-*.diff`（评审快照）→ `progress.md`（波次台账）。

- progress 一行式记录：`Task 4: complete (commits X..Y, review clean; minors deferred: ...)`；
- **deferred 逐条登记**，跨波移交项加粗单列写进下一波简报——不登记的延迟=丢失；
- 只增不改：台账是审计线索，不是 wiki。

## 六、文档地图

入口放一份"想找什么 → 看哪里"路由表，每行标注档位。增删移动文档必须更新此表（否则路由表本身开始撒谎）。

**📌 RagDemo 实例**：`docs/README.md` 以 17 行路由表覆盖全部文档，含档位列；顶层快照（如全量测试报告）不入活文档清单，靠日期前缀自证时点。
