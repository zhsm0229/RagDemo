# 设计 spec：要可裁决，不要散文

中等以上变更（跨模块、有行为变更、有多个可选方案）**先写 spec、评审冻结、再编码**。spec 的检验标准：评审者能对每一条说"同意/反对+理由"，编码者不需要再做任何设计决策。

## spec 骨架（九段，按序）

```markdown
# <变更名>（vN）
> 状态：<草案|评审中|已实施>｜配套文档指针｜**编码必须严格遵循本文档；
> 冲突先评审指出，不许静默择一**

## 1. 目标与非目标
   目标一句话；非目标显式列出（防范围蔓延，防评审扯皮）
## 2. 门槛分类
   A 资源门槛 / B 证据门槛（须评测数据）/ C 纪律门（永久不做）——
   每个"暂不做"都写明解锁条件
## 3-N. 方案
   以**参数表**表达：字段 | 类型 | 缺省值 | 说明
   **铁律：缺省值 = 现状行为**（见下）
## N+1. 测试 seams（冻结版）
   按测试层列出每条测试的断言口径；纪律行（TDD 中文标题/读回断言/Stub）
## N+2. 验收阈值
   量化验收线；首批数据到位后校准一次再冻结
## N+3. 裁决记录
   编号列表：裁决内容 + 来源（评审角色 + findings 编号）
## N+4. 独立工作包/挂起票
   不随本波实施的拆出，写明触发条件
```

## 三个关键机制

### 1. 缺省=现状（等价证明）

方案参数表的每个可调参数，**缺省值必须等于变更前的行为**。这样新代码合入时主路径行为零变化——等价证明由既有测试全绿承担，风险被压缩到"显式开启的新路径"上。

**📌 RagDemo 实例**：retrieval-policy 波的 `RetrievalPolicy` 七字段全部缺省=旧行为（top_k=20/ef_search=40…），合入时 1152 个既有测试全绿即为等价证明；新能力（multi_query、动态 top_k）全部默认关。

### 2. 测试 seams 冻结

spec 里预先写死"这个变更由哪些测试保护、每条断言什么口径"。**为什么在编码前冻结**：事后补的测试会迁就实现（测出什么写什么），事前冻结的测试才守得住设计意图。

### 3. 裁决记录（编号+角色溯源）

评审中每个分歧的裁决结果编号记录：`裁决 3：降级态拒答阈值取 0.63 而非 0.60（宁拒勿编红线优先；架构师 F2）`。

**为什么**：分歧会反复出现。有裁决记录，第二次讨论同一问题时直接引用编号，不再重新吵架；裁决溯源到评审角色，责任与上下文可查。

## 与其他纪律的接口

- spec 评审冻结后 → 按其"测试 seams"节生成工单（见 `pipeline.md`）；
- spec 的参数表若含会漂移的数字 → 对应守账测试（见 `docs-system.md`）；
- spec 落地后触发的规范变更 → 回写 standards 并登记（如门槛分类并入 §25）。

## 反模式清单

- **散文式 spec**：满篇"考虑""兼顾"，没有参数表和验收线——评审无从裁决；
- **边编码边改 spec**：spec 与代码漂移，spec 沦为事后说明书；
- **没有非目标**：评审会上"为什么不顺带做 X"反复消耗；
- **裁决不记录**：同一个问题三个波次吵三遍。
