# 开发流水线：从需求收敛到迭代收口

## 全流程

```
需求收敛 → 设计 spec（评审冻结）→ 拆工单 → 波次划分 → 多代理 TDD 波次
   → 评审裁决 → 提交（脚本通道）→ 门禁复跑 → 收口四件套 → 台账/报告归档
```

## 一、需求收敛：让用户做选择题，不做问答题

对模糊需求执行**三轮以内收敛提问**：每轮 2-3 个问题、**每问必须附推荐项**（"➡️ 推荐：X，因为 Y"）；用户回"按推荐"即全部采纳。

**为什么**：开放式的"你想要什么"把设计负担推回给用户；带推荐的选择题把负担留给出题方，收敛速度差 3-5 倍。

## 二、工单拆解：一票一文件，Step 1 就是失败测试

每张工单（brief）固定结构：

```markdown
# Task N：<标题>
**Files**：Create/Modify 精确路径清单（含夹具）
**Interfaces**：产出契约（函数签名/DTO/fixture 行为定义）
- [ ] Step 1：写入失败测试（直接内嵌测试代码——红必须是"功能未实现"式红）
- [ ] Step 2：跑测试确认 FAIL（对空库/空环境）
- [ ] Step 3：最小实现（DDL/代码逐条照抄 spec，不发挥）
- [ ] Step 4：测试 PASS（含读回断言）
- [ ] Step 5：提交（消息已写好，照抄）
```

**为什么 Step 1 内嵌测试代码**：把"测试怎么写"的决策留在派工时（信息最全的时刻），执行者只需照抄——工单的可执行性以此为极限。

**波次划分**：按**文件面互斥**分组，同波内工单不会改同一个文件——并行安全的前提不是约定，是物理隔离。

## 三、多代理团队公式（大波次）

用户指令形如："安排 PM 总协调、架构师技术总责、设计师 UI 把控、开发×N 代码开发、测试验收，团队统一协调，**先组织评审、刷新规范和文档，严格按照文档设计和规范进行编码**。"

分工与产出：

| 角色 | 职责 | 产物 |
|------|------|------|
| PM（主会话） | 总协调、派工、台账 | 工单发布、progress 台账 |
| 架构师 | 技术方案、落点/分层审查 | findings（编号 F1-Fn） |
| 设计师 | UI 交互约定 | findings（编号①-⑤） |
| 开发×N | 按波次 TDD 实现（文件面互斥） | task-report（RED→GREEN 证据） |
| 测试 | seams 确认、用例计划、验收 | findings + 验收判定 |

执行纪律：**先三方评审 findings → PM 裁决回写 spec → 才开工编码**；开发报告必须含偏差登记（发现上游文档错误：最小修复+同步修订上游+登记，不静默）。

## 四、评审

- 分级：普通变更 1 人批准；auth/迁移/规范/安全须 2 人含 owner；
- 意见三要素：`[Critical|Important|Minor] 文件:行 + diff 原文证据 + 可执行建议`；
- AI 预审可以参考，**批准必须人工**；
- 评审 diff 落台账（`review-<sha>..<sha>.diff`），意见必须落到 MR 评论不留私聊。

## 五、提交：脚本通道

波级收口用提交脚本（`.scratch/commit-<波次>.sh`），固定骨架：

```bash
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.."
git add <显式路径清单>          # 日常禁 git add -A；波级脚本例外但须 reset 排除台账/产物
git commit -m "<type>: <一句话>

<分节 body：每个特性块引 spec 章节号>

门禁：后端 pytest 全绿+覆盖率不降｜前端四门｜ruff 双绿
文档同步：<清单>｜台账：<指针>｜挂起票：<列表>"
git log --oneline -1 && git status
```

约定：Conventional Commits（`feat/fix/docs/refactor/test/chore: 简述`）；一个提交一件事；提交前 ruff 必过；禁直推 main。

## 六、收口四件套与偏离记录

收口四件套：全量回归+前端四门 → 打 tag → staging 部署+冒烟 → 迭代报告归 archive/。

**偏离记录纪律：偏离 SOP 必须写进偏离记录——不记录=违规，记录了=流程改进原料。** 📌 实例：`process-deviation-2026-10-01.md` 逐条记录"偏差内容/拦截发现/裁定/佐证/根治建议"。

## 七、验收报告的归因三态

测试/评审报告里每条问题按处置标注，避免抢改他人工作：

- `【已修复，当场】`——附修复说明；
- `【待修复】`——根因+建议修法+归属工单；
- `【并行会话在途，不抢改】`——待其收敛后复测。

**📌 RagDemo 实例**：2026-10-11 全量测试报告用三态归因，既修了 11 项又不碰并行车道的在途文件。
