# 项目启动三件套：入口文档 / 规范宪法 / 场景手册

新项目（或 AI 代理首次接手项目）的第一件事：把三份文档立起来。**三件套评审通过前不写业务代码**——这是全套方法论的第一个门禁。

## 三件套的分工

| 文档 | 角色 | 读者场景 | 特征 |
|------|------|---------|------|
| **AGENTS.md**（仓库根） | 入口汇总 | AI 代理/新人第一次接触项目 | 短（≤100 行）、指针化、含红线清单与唯一高频状态节 |
| **standards.md**（docs/） | 规范宪法 | 评审对照、架构决策 | 版本化变更日志、"违反=不合入"效力声明 |
| **playbook.md**（docs/） | 操作手册 | 干活时照抄命令 | 场景式路由表、命令可整体复制、模板区 |

三者关系：AGENTS.md 是 standards 的摘要与指针（冲突时以 standards 为准，且**冲突本身要提评审**，不许静默择一）；playbook 把 standards 的抽象条款翻译成"遇到什么事 → 照抄什么命令"。

## 一、AGENTS.md 怎么写

固定章节（顺序即阅读顺序）：

1. **头部三行元数据**：`定位｜对账日期｜同步保障`（如"当前状态节数字须守账测试背书"）；
2. **项目概览**：一句话产品定位 + 技术栈 + 演进纪律（如"设计按 100x 一次到位，建设按触发线分期"）；
3. **常用命令**：make/npm 六件套 + 增量测试原则（日常只跑改动相关，全量留给里程碑）；
4. **架构与分层**：分层图 + 接口化替换点 + 关键细则（行数红线、超时、禁跨层）；
5. **硬性红线**：5-8 条评审强制检查项（安全/数据/产品验收底线）；
6. **代码风格 / 测试 / 数据库 / 文档规范 / 提交**：各一节摘要，每条回指 standards 条款；
7. **当前状态**：全文唯一允许高频改写的段落，数字全部守账背书，末尾附并行会话警告（"改共享文件前先重读"）。

**写法要点**：写给 AI 与写给新人是同一份——AGENTS.md 的验收标准是"新人第一天读完能复述红线、答出流程关键关"。

## 二、standards.md 怎么写

- **效力声明置顶**："规范基线，违反=不合入"——没有效力声明的规范是建议；
- **版本化变更日志**：头部维护 v1.x→vN 逐版变更说明（变更内容+来源出处），规范演进可审计；
- **章节覆盖**：架构/代码/API/数据库/鉴权/安全/测试/文档管理/提交自查/演进（触发线与禁清单）等，按项目性质裁剪；
- **可检查性**：每条规范要么能 grep、要么能写测试断言、要么列为评审检查项——不可检查的条款降级为"建议"或删掉；
- **ADR 机制预留**：重大偏离写一页式 ADR（背景/选项/决策），归档可查。

## 三、playbook.md 怎么写

- **§0 路由表先行**："处境 → 章节映射"（第一天/领卡/修 bug/提交/评审/迁移/发布/收口/AI 规矩/模板/自测），目标 30 秒定位；
- **每个场景 = 可粘贴的命令序列**：命令带 `{{占位}}`，照抄即用，禁止"请酌情处理"；
- **模板复制区**：任务卡/MR 描述/发布单/迭代报告四大模板整体可抄；
- **AI 协作铁律单列**（一会话一卡/禁贴密钥/触达共享文件须声明/显式 add/批准须人工）；
- **自测门禁**：拿一张模拟任务卡走完全程，**任何一步卡住 = 对应章节写得不实，回来改手册**——手册自身的定稿门禁。

## 四、配套最小集

- `docs/README.md`：文档地图路由表（想找什么→看哪里，含档位列）；
- 目录骨架：`docs/specs/`（设计基线）、`docs/archive/`（快照归档）、台账目录（如 `.superpowers/sdd/`）；
- 守账测试的空位：为"端点总数/路由数"这类早期就会漂移的数字预埋契约测试。

## 五、三件套的生命周期

- 三件套随项目演进**走评审修订**（standards 版本号递增+变更日志）；
- 入口文档的"当前状态"节随里程碑收口更新；
- playbook 每次实战"卡住"都是修订信号——手册是活的，但改要走评审。

**📌 RagDemo 实例**：三件套 + docs/README 路由表 + `.superpowers/sdd/` 台账 + `tests/unit/test_api_contract.py` 守账，八波开发全程未出现"文档与实现谁对"的争论——有争论时裁决并回写，争论即消失。
