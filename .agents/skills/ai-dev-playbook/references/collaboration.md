# 对话协作：人机分工与多代理团队

AI 编码的失败模式几乎都不是"写不出代码"，而是**协作失序**：编造现状、跨卡操作、抢改并行车线、静默择一。本文件的纪律全部针对这些失败模式。

## 一、AI 会话四步走（每个任务固定开场）

1. **复述验收标准**——用自己的话把"做什么/做到什么程度"说回来，对不齐立刻纠正；
2. **只读探索给现状**——读代码/文档，报告"现在是什么样"，**一个字都不改**；
3. **产计划不写码**——给出步骤计划等人确认；
4. **人确认后才写码**。

**编造现状 = 立即纠偏**：AI 报告的"现状"若与实际不符（引了不存在的函数、猜了不存在的约束），当场指出并要求重查——编造一旦进入计划，后面每一步都在错误地基上施工。

## 二、一会话一卡

一个 AI 会话只处理一张任务卡，禁止跨卡操作。**为什么**：跨卡会话的上下文互相污染，改动边界失控，评审时无法把 diff 对齐到单一意图。

## 三、多代理团队公式（大波次开工令）

> "安排一个项目经理负责总协调、一个架构师负责技术总负责、一个设计师负责 UI 交互把控、三个开发人员负责代码开发、一个测试人员进行测试和验收，团队统一协调处理，**先组织评审、刷新规范和文档，严格按照文档设计和规范进行编码和后续所有任务**。"

要点拆解：

- **先评审后编码**：三方评审（架构师/设计师/测试）产出 findings → PM 裁决 → 回写 spec/规范 → 才开工。规范先行是团队模式的开关；
- **开发按波次、文件面互斥**：同波开发者不改同一文件，物理上消除合并冲突；
- **报告含偏差登记**：开发发现上游文档错误时——最小修复+同步修订上游+登记，不静默（📌 实例：test_config 陈旧断言随默认值演进，report 里写明"断言随默认值演进"）；
- **人每步 30 秒抽查**：抽验收标准、抽 diff、抽测试断言，"编造现状=立即纠偏"。

## 四、并行会话纪律

多会话（或多代理）同时工作在同一仓库时：

- **改共享文件前先重读**——你看到的版本可能已经旧了（git status 快照不更新，只有重读才算数）；
- **在途车道不抢改**：测试/评审报告里用归因三态（已修/待修/并行在途不抢改）标记问题归属；
- 重建类操作（docker build、依赖安装）输出**重定向到文件后显式检查退出码**——管道 `tail` 会吃掉失败信号。

## 五、安全与卫生

- **密钥/真实数据/生产库连接串禁贴 AI 对话**；密钥意外直贴时主动提醒脱敏并确认轮换；
- 日常提交**显式路径 `git add`，禁 `-A`**——波级收口脚本的批量 add 是例外，且必须 reset 排除台账/产物目录；
- 破坏性操作（删除/清库/重启）先核对证据再执行；对"看起来像已知问题"的信号确认根因后再动手。

## 六、与用户的沟通契约

- 中文交流；**结论先行**（第一句回答"发生了什么"），支持细节在后；
- 用户说"按推荐"= 全部采纳推荐项，不再逐条确认；
- 收敛式提问：每问附推荐项，让用户做选择题不做问答题；
- 报告失败如实写：测试红就贴红，跳过了步骤就说跳过——**报喜不报忧的代理不可复用**。
