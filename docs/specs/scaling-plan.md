# 规模演进规划（10x / 100x）— scaling-plan

> 版本：v1.0（待评审） · 日期：2026-09-28
> 关联：[standards.md §25 规模演进规范](../standards.md)、[project-brief.md](../project-brief.md)
> 结论：**主干架构不推翻**。设计时预留的接口退路就是为扩展准备的；需要动的是 6 个部位，按触发线分三阶段演进，禁止提前建设。

## 一、规模基线与 100x 量化

| 维度 | 试点（1x） | 100x |
|------|-----------|------|
| 用户 | 50-200 人 | 5 千-2 万人（全员） |
| 文档 / 向量块 | 1 千份 / ~5 万块 | 10 万份 / **~500 万块** |
| 提问量 | 每天数百次 | 每天 1-5 万次，峰值 QPS 5-20（对 LLM） |
| 部门 | 2 个（客服/HR） | 全公司 10-50 个 |
| 向量内存估算 | <2GB | 500 万 × 1024 维 ≈ 20GB 原始向量，HNSW 索引再翻倍 |

## 二、不变项（架构选型的验证）

- 五层架构、单向依赖、模块边界 —— 原样保留
- RAG 管道质量逻辑：分块、重排、引用溯源、拒答策略 —— 与规模无关
- 核心表结构 —— 以**加表为主**（ACL 表、同步源表、配额表），不改已有表
- 前端主体 —— 加页面，不重写
- 规范手册大部分章节沿用；需重写的只有部署、发布、备份三章

**已内置退路清单**（当前设计预留，演进时直接启用，任何新模块不得堵死）：
1. 六个可替换接口：`VectorStore` / `LLMProvider` / `Parser` / `Embedder` / `Reranker` / `FileStorage`（+auth 模块独立，SSO 替换位；+TaskQueue 抽象，BackgroundTasks→队列替换位）
2. 无状态 JWT 会话 → 应用层水平扩展开箱即用
3. auth 模块独立 → SSO 替换实现不动业务层
4. `dept` 字段粗隔离 → 细粒度 ACL 的演进基础
5. 审计记录 → 合规与排障基础
6. 合规轨道 `.env` 切换 → 云 API ↔ 内网模型零代码切换

## 三、必须演进的 6 个部位（含触发线）

### 1. 存储层：pgvector 拆出（最硬的一道墙）

500 万块向量 + HNSW 索引 ≈ 40GB 内存需求，与业务表混居单机必死。
- **触发线**：向量总量 > 200 万块，或向量内存 > 宿主机内存一半
- **动作**：启用 `VectorStore` 第二实现迁移 Milvus（standalone 起步）；业务库保留 PG；**pgbouncer 连接池 + 只读副本（messages 月分区已于 MVP 建成，见 db-design）**

### 2. 任务层：进程内后台任务 → 分布式队列

10 万份文档接入 + 常态化增量解析，BackgroundTasks 无重试/优先级/并发控制。
- **触发线**：日解析任务 > 200 份，或单次批量导入 > 5 千份
- **动作**：Redis + arq（或 celery）任务队列，解析独立 worker 池；MinerU 升级为可水平扩服务，量大时切 GPU 版

### 3. 算力层：推理从"一个容器"变"容量规划"

日 1-5 万次提问 ≈ 日 6 千万-3 亿 token，成本与吞吐都成为一等公民。
- **触发线**：日提问 > 5000 次（10x）即启动容量与成本测算
- **动作**：云 API 轨道 → 企业配额 + 按部门限流与成本核算；内网轨道 → vLLM 多卡集群（70B 级 4×A100，或 32B 换吞吐）
- **必做的省钱动作**：语义缓存（相似问题复用答案，客服场景可省 30-60% token，替代 §17.5 的精确匹配缓存）；问答对通道前置（FAQ 命中不进 LLM 链）；embed/rerank TEI 升级 GPU 多副本

### 4. 权限层：部门标签 → 细粒度 ACL + 强制 SSO

两部门时粗隔离正确；全员开放后跨部门协作成常态，粗隔离变阻碍；2 万人无法管理员发账号。
- **触发线**：试点两部门之外**第三个部门**接入时评估；全员推广前必做
- **动作**：新增 `document_acl` 表，检索过滤从 `WHERE dept IN` 演进为 ACL 判定；SSO 接入（auth 模块替换实现）；组织架构从 HR 系统自动同步

### 5. 语料层：手动上传 → 源系统自动同步

10 万份文档手动上传不可维护。
- **触发线**：文档总量 > 1 万份，或接入部门 > 5 个
- **动作**：连接器（wiki / 共享盘 / Confluence 等，挂在 `Parser` 接口旁新增 `Connector` 接口）；增量检测 + webhooks；文档 owner 工作流与到期自动下架（治理从约定变平台功能）

### 6. 运维层：单机 compose → 高可用 + 可观测

全员系统宕机即全公司事件。
- **触发线**：A 阶段（10x）即开始；C 阶段（100x）完成 HA
- **动作**：app 多实例 + 负载均衡（无状态 JWT 直接水平扩）；PG 主备自动切换；Prometheus/Grafana + Loki 监控告警；CI/CD 多环境晋升（staging → prod）；全链路压测；规范手册部署/发布/备份三章按新形态重写

## 四、三阶段演进路线（按触发线，不按日历）

| 阶段 | 大致规模 | 动作清单 |
|------|---------|---------|
| A（~10x） | 2 千人，推广初期 | app 多实例 + 负载均衡；**FileStorage 切共享存储（多实例前提）**；任务队列；SSO；登出黑名单/缓存迁 Redis；语义缓存；监控告警 |
| B（~30-50x） | 5 千-1 万人 | 迁 Milvus；pgbouncer + 只读副本（messages 分区 MVP 已建成）；细粒度 ACL；同步连接器；CI/CD 多环境 |
| C（100x） | 2 万人 | PG 主备与多机化（或 K8s）；GPU 推理集群；部门配额与成本核算；全链路压测 |

每个触发线到达时：写 ADR → 修订 standards.md 受影响章节 → 评审 → 实施。

## 五、禁止提前建设清单（YAGNI 纪律）

Milvus、K8s、微服务拆分、细粒度 ACL、语义缓存（A 阶段前用精确匹配 TTL 缓存）、自动同步连接器、GPU 推理集群、只读副本、多环境晋升流水线。
——与 MVP 不提前上 Milvus 是同一条纪律：每项都有明确触发线（见第三节），到线才做。

## 六、技术之外的硬前提

1. **LLM 成本**：100x 场景月度 token 成本为数万元级（云 API 轨道粗估），或内网 GPU 集群采购决策。**A 阶段（10x）时即需与管理层对齐预算**，不能等到撑不住。
2. **团队**：试点期 1-2 人 + AI 辅助；30x 起至少专职后端 ×2、前端 ×1、运维 ×0.5。团队不扩，架构演进无从谈起。
3. **决策复审点**：全员 2 万人规模时，"自研 vs 商业平台（RAGFlow/Dify 商业版等）"应重新上会评估一次；带接口退路的自研资产是评估时的底牌与谈判筹码。
