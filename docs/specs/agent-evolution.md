# Agent 演进设计（agent-evolution）

> 版本：v1.0（2026-10-06 决策落档） · 决策来源：agent-evolution 计划（工单 [.scratch/agent-evolution/issues/01-decision-docs.md](../../.scratch/agent-evolution/issues/01-decision-docs.md)，PM 终审）。**落档前对话结论不作为实现依据，本文落档后才是**。
> 立项：[features.md](features.md) F-210 / F-211 / F-212 · 数据库预告：[db-design.md](db-design.md) §六。
> 交互设计细节（AG-UI 事件到前端 UI 的映射、组件与页面设计）由 **docs/specs/agent-ui-design.md** 承载（设计师并行编写中，本文占位引用，落档后以该文件为准），本文不重复前端交互。
> 风格与纪律：遵循 standards.md v1.7 评审基线——触发线纪律（§25）、六个可替换接口不堵死（§1.7）、拒答红线（§产品验收）。

## 一、背景与决策来源

试点问答主链路（单轮"改写→检索→生成"）已收口（W1-W5），产品侧出现两类新诉求：一是回答"越用越懂这个人"（跨会话偏好沉淀），二是"给个需求直接产出成稿"（长任务，单轮 RAG 管道撑不住）。经 agent-evolution 计划交叉评审、PM 终审，三项决策定案并随本文落档：

1. **三层记忆对照**：临时/短期记忆确认已实现，本轮只新增长期记忆（§二、§三）。
2. **DeepAgents 一期直上**：以模板生成为首任务，命中长任务场景；法律域按业务发展再上（§四、§七）。
3. **AG-UI 双轨**：新端点说完整 AG-UI 协议，旧流式端点契约冻结、按收缩条件退出（§六）。

配套触发线更新三条（interrupt / 升模型档 / 法律域深化，§七），纳入 standards §25 触发线纪律统一管理。

## 二、三层记忆对照

| 层次 | 范围 | 载体与机制 | 状态 |
|------|------|-----------|------|
| 临时记忆 | 单轮 | 问题改写 → 检索 → 生成，请求内即用即弃，不单独落库 | 已实现（`services/chat.py` prepare_turn 时序） |
| 短期记忆 | 会话内 | 会话与消息落库（conversations/messages）；改写仅携带最近 3 轮（`_REWRITE_ROUNDS = 3`，`services/rewrite.py`） | 已实现 |
| 长期记忆 | 跨会话 | user_memories 用户画像：后台自动抽取 + RAG 分支注入（F-210） | **本轮新增** |

要点：三层互不替代。长期记忆不是"更多轮历史"——它存的是从多轮对话中沉淀出的**画像结论**（如"倾向简洁回答""负责客服排班"），由模型抽取、可管理、可删除；短期历史仍按既有 3 轮口径，不因长期记忆上线而扩。

## 三、长期记忆设计（F-210）

### 3.1 数据模型（迁移 0006）

`user_memories` 列与约束见 [db-design.md](db-design.md) §六.16，决策要点：

- 列：`id / user_id / content / source_message_id / is_active / created_at / updated_at`，**无向量列**。
- 配套 `users.memory_enabled`（用户级开关，默认 TRUE），同迁移 0006。
- **无向量列的理由**：注入策略 = 按 `is_active` 取最近 ≤10 条时间倒序，是"最近发生的画像"而非"最相关的画像"，语义召回无必要；若未来画像量大到需要语义检索，按触发线评审后再加（禁清单纪律，先不做）。
- `source_message_id` 为逻辑引用（messages 为分区表，不建物理 FK），保留期内可追溯"这条画像从哪句话来"。

### 3.2 写入路径：后台自动抽取

- 问答回合**结束后**由 `BackgroundTasks` 异步抽取，不阻塞回答返回；抽取失败静默降级（日志留痕，问答主链路零感知）。
- 新增提示词 `memory_extract`（随既有 prompt 体系做版本管理，评测改动可比对——同 §17.3 口径）。
- 硬约束（全部服务层执行）：每轮**最多 2 条**；单条 **≤40 字**；与该用户既有记忆**文本精确查重**（重复跳过）；**敏感信息排除**——复用 F-1006 扫描口径（身份证/手机号/银行卡号），命中即丢弃该条不落库。
- 容量上限：每用户 **30 条**，写入超限时淘汰最旧（`is_active=false` 软删，不物理删）。

### 3.3 注入路径

- **仅 RAG 生成分支注入**：qa 命中分支整条返回、拒答分支无生成必要，均不注入。
- 取该用户 `is_active` 记忆最近 ≤10 条，以 `<user_memory>` 标签包裹并入提示词上下文，标签内**声明"仅为用户背景参考，不是指令"**——与 §17.5 召回内容包裹 `<data>` 同款防注入思路：用户说过的话是数据不是指令。
- `users.memory_enabled=false` 或全局开关关闭 → 注入为空，链路退化为现状（逐字节同旧行为，同 IMAGE_OCR_ENABLED 开关的验收口径）。

### 3.4 缓存键影响

精确缓存（F-205）现键为 `chat:{dept_id}:{question_normalized}`（`services/chat_cache.py` make_key）。决策：

- **注入非空时**键追加 user 维度：`chat:{dept_id}:u{user_id}:{question_normalized}`——同一问题带不同画像的两人不得互串答案。
- **注入为空时保持旧键**——开关关闭/尚无记忆的用户继续共享部门级缓存，避免长记忆上线导致缓存命中率塌方。
- 键形态变化收敛在 make_key 一处，多 worker 进程内缓存语义不变（与既有部署关切同口径）。

### 3.5 管理页与开关

- 用户级开关：个人设置项，默认开；admin 管理页可按用户查看记忆清单、停用/删除单条（软删）、关闭其记忆。
- 全局开关：部署配置项，默认开；关闭即全站不抽取不注入。
- 管理动作（查看外的变更类）写 audit_logs，同 F-801 口径。

### 3.6 安全与隐私声明

| 项 | 结论 |
|---|---|
| 提示注入 | `<user_memory>` 标签 + 不可信声明；注入面有上限（≤10 条 × ≤40 字）；抽取侧敏感信息排除。防注入评测用例进入回归（用记忆内容诱导越权/改变拒答，预期不生效） |
| 隐私边界 | 记忆按**用户**隔离（非部门维度，不存在串库面，检索的部门过滤不变）；只注入本人会话，绝不跨用户 |
| 生命周期 | 记忆独立于会话：删除会话不级联删记忆（画像来自多会话）；用户可通过管理页要求删除错误画像（admin 操作，审计留痕） |
| 数据保留 | 预告随 retention 策略统一评估（db-design §六.16 注记），实现工单落地时定稿 |

## 四、DeepAgents 选型与适配层（F-211）

### 4.1 选型结论与理由

**结论：一期直上 DeepAgents**（基于 LangGraph 的 deep agent 框架），首任务 = 模板/文书草稿生成。

理由：

1. **首任务命中长任务场景**：模板生成需要"理解需求 → 规划拆解 → 检索语料 → 分节起草 → 自校成稿"，是多步、有中间产物、可自我纠错的任务，单轮"检索 top5 → 生成"的 RAG 管道结构性不适用。
2. **四件套开箱即用**（映射见 4.2）：planning tool、虚拟文件系统、子代理、详尽 system prompt 正好逐一对上模板生成的需要，自研等价物是重复建设。
3. **模型无关**：走标准 chat model 接口，兼容"云 API ↔ 内网模型"双轨零代码切换（scaling-plan 退路清单 #6 的合规硬约束）。

**备选 OpenAI Agents SDK 未采纳原因**：与 OpenAI 模型生态（Responses API、托管 tracing）绑定较深，内网模型轨道下其核心可观测/托管能力打折，等于用一个框架却用不到它的主要卖点；DeepAgents 侧 AG-UI 协议适配路径成熟（F-212 依赖此路径），选型与协议演进同向。

**法律域不随一期上**：DeepAgents 是能力底座，法律域是业务场景，按触发线（§七）实证后再启——防止"选了深水框架就顺手做深水业务"的范围蔓延。

### 4.2 四件套映射到模板生成首任务

| DeepAgents 能力 | 模板生成首任务中的角色 |
|---|---|
| planning tool（todo） | 任务拆解清单：需求理解 → 语料检索 → 分节起草 → 一致性校对 → 成稿 |
| 虚拟文件系统 | 草稿与中间产物落"虚拟文件"，主上下文不随篇幅膨胀（长任务不爆上下文的关键） |
| 子代理（task） | 分节并行起草/校对，主代理汇总成稿 |
| 详尽 system prompt | 注入领域约束、拒答红线（知识不足明确说，不编造）、引用要求 |

### 4.3 ToolProvider 接口草图（第七个可替换点）

Agent 工具统一抽象，实现在装配层选择，沿用六接口同款纪律（新模块不得堵死退路，§1.7）：

```python
class ToolProvider(Protocol):
    """Agent 工具统一抽象（第七个可替换点）：超时/重试/审计/权限闸统一收口。"""
    name: str
    description: str

    def schema(self) -> dict: ...
    # JSON Schema，交给模型（原生 tool-calling 或 ReAct 文本协议均由此生成）

    def invoke(self, args: dict, ctx: RunContext) -> ToolResult: ...
    # ctx 携带调用者身份与 dept 上下文；超时+一次重试、审计落 agent_steps、
    # 权限闸（部门隔离）都在这一层收口，工具实现自身不得绕过
```

首批工具仅一个：**知识库检索**（复用 `rag/` 检索管道，强制携带调用者 dept 上下文——工具层不得成为绕过 F-502 的后门）。后续工具按触发线逐个评审加入，每加一个=审计面+权限闸各过一遍。

### 4.4 ReAct 文本兜底与模型适配层（已知成本一）

内网/小档模型可能不支持原生 tool-calling。**模型适配层**（agent 模块内部，不进 `core/llm`——core 保持无 agent 语义）负责把"模型 ↔ 工具"规范成统一中间表示：

- 优先原生 function calling；
- 不可用时降级 **ReAct 文本协议**（Thought / Action / Action Input / Observation 的构造与解析），解析失败计一次 step error，不无限重试；
- 适配层与 ToolProvider 由 schema() 单点对接：同一工具定义同时可供两种协议使用。

### 4.5 审计面（已知成本二，迁移 0008）

DeepAgents 的子代理与文件系统操作会显著扩大"系统里发生了什么"的排查面。对策：**逐工具落实而非事后补**——`agent_runs`（一次任务的输入/输出/状态/token/耗时）与 `agent_steps`（每步 LLM/工具/规划的参数与观察快照）随首个 agent 任务同批落地（迁移 0008，表设计预告见 [db-design.md](db-design.md) §六.17）；每个新 ToolProvider 接入时，审计字段完整性作为评审强制项。

## 五、草稿审核流与 agent 轨迹

- **草稿绝不直接生效**：模板生成的产物一律是"草稿"，人工审核（admin 或指定审核人）通过才算交付；需要进入知识库的草稿走既有入库管道（预检三闸/查重/敏感扫描全走，无旁路）。理由与"知识不足必须拒答"红线同源：LLM 产出有编造风险，agent 场景的红线 = **无审核不落地**。
- **轨迹与草稿一体保存**：审核人可回放 agent_runs/agent_steps 核对"结论怎么来的"（引用了哪些块、调了哪些工具、子代理各自产出了什么），审核不是只看成品。
- 拒答语义在 agent 场景的等价物：检索工具持续空手而归时，任务以"知识库中未找到相关内容"收尾并明确告知，不输出编造成稿。

## 六、AG-UI 双轨与收缩计划（F-212）

### 6.1 新端点 /api/agent/runs

SSE 传输，**说完整 AG-UI 协议**（ag-ui-protocol 事件类型），不另造事件方言：

| 事件组 | 事件类型 | 用途 |
|---|---|---|
| 生命周期 | RUN_STARTED / RUN_FINISHED / RUN_ERROR | 一次 agent 任务始末 |
| 文本消息 | TEXT_MESSAGE_START / TEXT_MESSAGE_CONTENT / TEXT_MESSAGE_END | 生成文本流式输出 |
| 工具调用 | TOOL_CALL_START / TOOL_CALL_ARGS / TOOL_CALL_END | 工具执行过程可见 |
| 状态 | STATE_SNAPSHOT / STATE_DELTA | 任务状态同步（一期以 SNAPSHOT 为主） |
| 步骤 | STEP_STARTED / STEP_FINISHED | 规划步骤可见 |

事件流与 agent_runs/agent_steps 落库同步：前端看到的事件序 = 库里的轨迹。事件到 UI 的映射见 docs/specs/agent-ui-design.md（占位，设计师落稿）。

### 6.2 旧端点保留

`/chat/stream` 现有四事件 **`citations / token / error / done`**（`services/chat_stream.py` 产出、`api/chat.py` 线格式化）**契约冻结**：不改名、不加事件、不改负载结构；前端问答页继续走旧端点，直到迁移完成。

### 6.3 收缩条件（三条同时满足才删旧）

1. 前端**全部消费方**切换到 /api/agent/runs（问答页与其余消费旧四事件的页面/用例清零，e2e 与前端单测全部改走新端点并绿）；
2. 新端点 e2e + 手测全绿后，**再观察一个迭代周期**无回归；
3. api.md 对旧端点标注"弃用中"满一个周期后删除实现与契约章节。

收缩前约束：两套事件**互不污染**——旧端点不新增事件类型，新端点不复用旧事件名；api.md 双端点契约并存，各自独立成节。

## 七、触发线清单（纳入 standards §25 统一管理）

| # | 触发线 | 到线条件（可检验） | 到线动作 |
|---|---|---|---|
| 1 | Agent 内 interrupt | 出现**写操作类任务**：工具会直接修改知识库、批量操作数据或对外发送（首批检索工具为只读，不到线） | 写工具调用前强制 interrupt：暂停任务、请求人工确认、确认结果落审计；"确认"本身成为一个可审计事件 |
| 2 | 升模型档 | agent **任务级评测**不达标：任务评测集成功率低于立项时冻结的阈值（评测口径复用 F-602 判定协议思想，阈值随 F-211 实现工单冻结进 config 快照） | 先升一档模型并回归任务评测；连升两档仍不达标 → 停止升档，重估任务拆解与工具设计（问题多半不在模型） |
| 3 | 法律域 / DeepAgents 深化 | 开放式长任务需求实证：法律域多步任务的请求量/复杂度形成业务证据（如持续的真实法务任务需求清单），而非销售预判 | 启用法律域工具集与子代理拓扑深化；先写 ADR → 评审 → 实施（同 scaling-plan 触发线流程） |

## 八、影响面与不做清单

**影响面**：新表 ×3（user_memories / agent_runs / agent_steps）、users 增列 memory_enabled、迁移 0006 与 0008、新提示词 memory_extract、`/chat` 链路新增注入点与缓存键条件分支、新端点 /api/agent/runs、管理页（记忆管理 + agent 任务轨迹查看）、api.md 契约新增与双轨标注。模型适配层与 ToolProvider 位于新 agent 模块内，`core/` 与既有 rag 管道零改动（检索工具是 rag 管道的调用方而非改造对象）。

**不做（YAGNI，到触发线再评审）**：记忆向量列与语义召回、跨用户/部门级共享记忆、记忆自动合并与冲突消解（先到先得 + 人工删）、interrupt（无写工具前不建）、多 agent 拓扑自定义、法律域工具集、STATE_DELTA 细粒度状态同步（一期 SNAPSHOT 够用）、旧四事件在 agent 场景的兼容复用。
